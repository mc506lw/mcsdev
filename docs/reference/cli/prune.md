# `mcsdev prune`

清理「mcsdev 部署过、但当前配置已经不再产出」的残留 jar。**不会碰手工放进 `plugins/` 的文件。**

```
mcsdev prune [options]
```

## 参数

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `--dry-run` | 开关 | 关 | 只列出将删除什么，不动文件 |
| `--yes` | 开关 | 关 | 跳过确认（默认会问一次，默认答案是否） |

## 判定依据

只认部署清单 `<link>/plugins/.mcsdev-manifest.json`。清单里记录的每个文件，如果满足下面任一条件就是候选：

| 条件 | 打印的原因 |
| --- | --- |
| 该文件路径不在当前配置的产出集合里，但归属的 id 还在配置里 | `<id> 的旧版本（当前配置不再产出）` |
| 归属的 id 整个不在配置里了 | `entry「<id>」已从配置里删除` |

候选还必须**在磁盘上真实存在**才会被列入（你手动改成 `.jaroff` 的文件不在其中）。

## 输出

```
  配置  E:\dev\pylon\mcsdev.yml
  目标  E:\Minecraft\开发\Pylon开发\plugins

将删除 2 个残留 jar：
  − Lapis-Legacy-0.3.1.jar   (entry「legacy」已从配置里删除)
  − Lapis-Pipez-0.1.50.jar   (pipez 的旧版本（当前配置不再产出）)
```

`--dry-run` 到此为止；否则确认后逐个删除：

```
? 确认删除这 2 个文件？ › 否
```

## 前置条件

### 配置必须没有错误

```
✖ config: 尚未实现 —— 当前版本不会把这些键写进 server.properties。请删掉这一段（等 v0.2）
  ? 配置有错时不建议 prune —— 先修好，否则"当前配置"不可信
```

退出码 1。理由是 `prune` 完全依赖「当前配置产出什么」做判断，配置坏了这个判断就是错的。

### 必须有部署清单

清单为空时不做任何事：

```
mcsdev 没有部署记录（manifest 为空）—— 无法安全判断哪些 jar 是 mcsdev 放的
  ? 先跑一次 mcsdev deploy 建立记录；手工放入的插件永远不会被 prune 碰到
```

退出码 0（这不是错误，只是无事可做）。

清单在 `deploy` / `dev` 每轮结束时更新：**只要该条目这一轮没失败**（哪怕是「已是最新」）就会补记。所以换机器、删过清单之后，跑一次 `mcsdev deploy` 就能把当前配置产出登记为「mcsdev 放的」。

### `plugins/` 目录不存在

```
✔ plugins/ 目录还不存在，没有可清理的东西
```

退出码 0。

## 不会删的东西

| 文件 | 为什么 |
| --- | --- |
| 手工放进 `plugins/` 的 jar | 不在清单里 |
| `Foo.jaroff` | 清单记的是 `Foo.jar`，该路径已不存在 |
| 插件自己生成的配置目录（`plugins/MyPlugin/`） | 只处理清单里的文件路径 |
| 当前配置仍然产出的文件 | 在 `keepRel` 集合里 |

## 删除之后

被删的 jar 如果已经在 JVM 里加载着，删文件不会卸载它。所以：

```
✔ 已清理 2 个残留 jar
  ? 重启服务器后生效：mcsdev restart（或让 dev 处理）
```

## 退出码

| 情况 | 退出码 |
| --- | --- |
| 清理成功 / 没有残留 / 没有清单 / 没有 `plugins/` | 0 |
| 配置解析失败 | 1 |
| 配置有错误 | 1 |
| 用户在确认时选「否」 | 0（打印「已取消」） |

## 与 `clean` 的区别

| | `clean`（`plugins[].clean`） | `prune` |
| --- | --- | --- |
| 触发时机 | 每次部署 | 显式执行 |
| 清理对象 | 目标目录里 `<prefix>*.jar` 的旧版本 | 清单里、配置已不再产出的文件 |
| 依据 | 文件名前缀 | 部署清单 |
| 能清掉「整条 entry 被删掉」的残留 | 不能（没有条目就没有前缀可推） | 能 |

两者互补：`clean` 处理「同一个插件的旧版本」，`prune` 处理「已经不存在的条目」。
