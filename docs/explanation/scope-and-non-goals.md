# 边界与非目标

mcsdev 是一个**本地、单用户、终端优先**的开发辅助工具。这个边界决定了它做什么，也决定了它拒绝做什么。

## 明确不做

| 不做 | 为什么 |
| --- | --- |
| **不是服务器插件** | 它不进服运行，不注册监听器，不影响服务器行为。卸载它就是删掉一个命令行工具 |
| **不是运维面板** | 没有 Web UI、没有多用户、没有备份调度、没有端口转发、没有远程管理。那些是 MCSManager / Pterodactyl 的领域 |
| **不面向生产部署** | 它的所有假设都指向「开发机上的测试服」：默认离线模式、默认强杀兜底、默认不备份 |
| **不做热重载** | 类加载器不卸载，reload 换来的是玄学 bug，不是速度。见[为什么重启而不是热重载](/explanation/why-restart-not-hot-reload) |
| **不做构建** | 除非你显式配 `dev.build`，它只消费构建产物，不替你跑 gradle |
| **不是测试框架** | 它验证「服务器能加载这个插件」，不验证「逻辑正确」。单元测试用 JUnit + MockBukkit，集成测试用 paper-test-lib |
| **不支持 Fabric / Forge** | 只面向 Bukkit 系（Bukkit / Spigot / Paper / Folia / Leaf） |
| **不做备份与回滚** | `plugins/` 的旧 jar 会被清理，没有历史版本可回退 |

## 已知限制

这些是**当前版本的实现限制**，不是设计选择。它们被列在这里，是因为知道边界比读一堆「支持 X」更有用。

### 环境与平台

| 限制 | 表现 | 规避方式 |
| --- | --- | --- |
| 就绪探测超时会阻塞 `dev` 的排队变化 | `dev` 一轮里的重启会一直等到端口可连（最多 120s），期间检测到的变化只能排队 | 探测连不通时用 `restart.type: command` 让脚本自己等，或 `none` |
| Windows 上跨进程停止一律是强杀 | `mcsdev stop` / `mcsdev restart` / `deploy` 触发的重启都走 `taskkill /T /F`，世界可能未保存（会警告）；只有 `run` / `dev` 自己持句柄时才能优雅停 | 用 `restart.type: command` 调一个自己会优雅停的脚本；或用 `run` / `dev` 托管 |
| 启动前不校验 JDK 与 MC 版本 | 版本不匹配时服务器自己退出，日志里是 `UnsupportedClassVersionError` | 用 `mcsdev java use` 切到正确的 JDK；见[管理 JDK](/how-to/manage-jdk) |
| `new` 依赖 PaperMC API | 网络不通时无法拉版本列表 / 下载 jar | `MCSDEV_PAPER_BASE` 指向镜像 |
| 无 `mcsdev rm` | 删除实例要手动删目录 + 手改 `instances.json` | 暂无命令（设计里排在后续版本） |

### 配置能力

| 限制 | 表现 |
| --- | --- |
| `config:` 字段未实现 | 写了直接报错，不会写进 `server.properties` |
| `onStart:` 字段未实现 | 写了直接报错，不会执行 |
| `configApply:` 写了会报错 | 未实现，和 `config:` / `onStart:` 一致 |
| `java install` 未实现 | 需要自己装 JDK |
| `to:` 已移除 | 写了直接报错（Bukkit/Paper 不加载子目录里的 jar） |
| `prune` 没有 `--adopt` | 手工放进 `plugins/` 的历史 jar 只能自己删，`prune` 只认清单 |

### 并发与状态

| 限制 | 表现 |
| --- | --- |
| `dev` 是轮询，不是文件系统事件 | 默认 500ms 一次，变化感知有最多半秒延迟；目录很大时轮询成本上升 |
| 部署清单需要「先部署过」 | `prune` 在清单为空时什么都不做（跑一次 `deploy` 即可建立） |
| `exec` 走 dev 会话的 IPC 时不回传服务器输出 | 命令确实进服了，但输出只出现在 `dev` 那个终端里 |
| 无部署历史 | 不知道「上一版是什么」，无法回滚 |

### 退出码

错误路径统一返回 **1**：`run` / `new` / `java` / `start` / `stop` / `restart` / `logs` / `rebuild` / `reset` 在「未 setup / 找不到实例 / 找不到 jar / 未知 action」时，和 `config` / `ps` / `deploy` / `dev` / `prune` / `exec` 一样以退出码 1 结束。

所以脚本里可以放心用 `mcsdev <cmd> && 下一步`。唯一的例外是纯提示性的情况（比如 `ps` 报告「有 5 个条目落后」、`logs` 说「还没有日志文件」）—— 那些不是错误，退出码仍然是 0。

## 什么时候不该用 mcsdev

- **你在部署到生产服**：没有备份、没有审计、默认离线模式、强杀兜底。用正经的部署流程。
- **你要写集成测试**：paper-test-lib 更合适 —— 它能断言、能进 CI、不依赖一台长期运行的服务器。
- **你需要热重载**：这个需求 mcsdev 明确不支持，别指望它。
- **你的服务器在另一台机器上**：部署能成功，就绪探测也能用 `host` 指过去，但优雅停服仍然打折（跨进程只能强杀）。
- **多人共用一台开发服且互相不知道**：mcsdev 假设你对目标 `plugins/` 有独占权。别人也在往里丢 jar 时，`clean` 和 `prune` 的判断可能不符合预期（虽然 `prune` 有清单保护，`clean` 只按前缀删）。

## 边界是怎么画出来的

判断一个新功能该不该进 mcsdev，用三个问题：

1. **它服务「构建 → 验证」这个循环吗？** 不服务的（备份、监控、远程管理）出去。
2. **它需要多用户或网络服务吗？** 需要的出去 —— 那会把它变成一个面板。
3. **它的失败能不能被本地的、即时的检查发现？** 能（端口探测、哈希判等、配置校验）就留下；不能（比如「这个改动在 30 天后会不会出问题」）就不属于这里。
