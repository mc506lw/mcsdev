# 为什么用 sha256 判等而不是 mtime

「这个 jar 已经是最新的了吗？」这个判断，mcsdev 用**文件内容哈希**（sha256）做，不用时间戳。

## mtime 判断为什么不可靠

「目标文件比源文件新就算最新」是最自然的实现，也是错的。四种真实场景会让它错：

### 1. Gradle 构建缓存

Gradle 的 build cache 会把之前构建过的产物**直接复制回来**，复制会保留原始 mtime。于是：

```
build/libs/MyPlugin-1.2.0.jar   mtime = 三天前（缓存里的）
plugins/MyPlugin-1.2.0.jar      mtime = 今天（上次部署时复制的）
```

按时间判断：目标更新 → 「已是最新」→ **跳过部署**。而实际上 `build/libs` 里那份可能是你刚改完代码、重新构建出来的新内容。

### 2. `git checkout` / `git clone`

git 不保存 mtime。切分支、重新 clone 之后，所有文件的 mtime 都是「刚才」。如果 `build/libs` 里的 jar 被 git 跟踪（有些项目确实提交 jar），一次 checkout 就能让所有产物的 mtime 变成同一秒。

### 3. 跨机器复制

从另一台机器拷过来的 jar，mtime 可能保留（`cp -p`）也可能重置（U 盘、网盘同步、`scp` 的某些配置）。

### 4. 系统时钟

双系统、虚拟机快照回滚、CI runner 时钟漂移 —— 都会让「谁更新」这个问题失去意义。

## 这些错误的代价

注意失败的形状：mtime 判断错误的方向几乎总是**「误判为已是最新」**，也就是**静默跳过部署**。

你不会看到任何错误。你只会看到：

```
· pipez: 已是最新
```

然后你去游戏里测试，发现新写的命令不存在，开始怀疑：

- 是不是构建没成功？（重新 build 一次，还是「已是最新」）
- 是不是插件没加载？（看日志，加载了）
- 是不是我的命令注册写错了？（看代码，没写错）
- 是不是服务器没重启？（重启了）

二十分钟后你才会想到「也许根本没部署」。而真正的解法只需要一行：`mcsdev deploy --force`。

**静默的错误比显式的失败贵得多** —— 这是 mcsdev 大多数默认值背后的同一条原则。

## 哈希的成本

sha256 算一个 5 MB 的 jar 大概几十毫秒。部署是「人按了一次构建」这种频率的事件，一次 `dev` 轮次算 8 个 jar 也就是几百毫秒，完全可接受。

而且 mcsdev 还加了一个便宜的前置判断：

```ts
same = a.size === b.size && sha256File(src) === sha256File(dest);
```

大小不同直接判定不同，不做哈希。大小相同才去算哈希 —— 而大小相同、内容不同的情况确实存在（比如只改了一个字符长度的常量，或者版本号字符串等长替换），所以不能用大小代替哈希。

## 哈希用在哪，时间用在哪

这里有一个容易混淆的点：mcsdev 在**两个地方**判断「变化」，用的是**不同**的手段，而且是刻意的。

| 场景 | 判据 | 为什么 |
| --- | --- | --- |
| 「目标文件是否需要更新」（`deploy`、`ps`） | **sha256** | 关心的是「内容是否相同」，必须准确，错了会静默跳过 |
| 「多个匹配产物里哪个最新」（`newest`） | **版本号**，解析不出才回退 **mtime** | 关心的是「哪个是更高版本」，这是构建产物的固有属性，不该被文件时间左右 |
| 「产物目录是否变化」（`dev` 的轮询） | **文件名 + 大小 + mtime 的快照** | 每 500ms 一次，必须便宜；这里允许误报（多部署一轮），不允许漏报 |

三处判断回答的是三个不同的问题：

- 内容是否相同 → 哈希；
- 哪个是更高版本 → 版本号（没有版本号才退回时间）；
- 有没有动过 → 廉价快照。

用错工具的地方才会出问题：用时间回答「内容是否相同」会静默跳过部署；用时间回答「哪个是更高版本」，就会在上面的 build cache 场景里选错产物 —— 而这恰好和部署阶段的哈希判等打架（选了个旧的，然后被告知「已是最新」）。所以 `newest` 现在先比版本号，版本号解析不出来才退回 mtime，并在警告里明说用的是哪个依据（「按版本号取最新的 X」/「按修改时间取最新的 X」）。

## 一个副作用：`ps` 也用哈希

```
  id       构建产物                 已装                     状态
  pipez    Lapis-Pipez-0.1.59.jar  Lapis-Pipez-0.1.59.jar   最新
```

`ps` 的 `最新` / `落后` 也是哈希比出来的，所以它和 `deploy` 的判断永远一致。如果 `ps` 说「最新」，那么 `deploy` 一定会跳过它 —— 这两件事不会是两种口径。

## 什么时候你会想用 `--force`

`--force` 绕过哈希判断，无条件重装。合理的用途：

- 想强制重装一遍所有条目（清单在「已是最新」时也会补记，所以通常不需要 `--force` 做这件事）；
- 目标文件被外部工具改过、但内容恰好与源文件相同；
- 你在排查「到底是不是判等的问题」，需要排除这个变量。

不合理的用途：日常部署。哈希判断是准确的，`--force` 只是多花时间。
