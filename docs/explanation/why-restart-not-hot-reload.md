# 为什么重启而不是热重载

mcsdev 的循环是「部署 → 重启」，不是「部署 → `/reload`」。这是刻意的，也是它最容易被质疑的一个决定：重启明明更慢。

## 热重载在 Bukkit 系上到底发生了什么

`/reload` 做的是：卸载所有插件 → 重新读取 jar → 重新加载。问题在于**「卸载」在 JVM 上不成立**。

### 类加载器不会被回收

Bukkit 为每个插件建一个 `PluginClassLoader`。卸载时它会被丢弃引用，但：

- 只要还有一个对象引用着插件里的类（一个没取消的 task、一个静态缓存、一个被别处持有的 listener），整个 classloader 就无法被 GC；
- 插件的静态字段（`static Map`、单例、注册表）会随着 classloader 一起留在内存里；
- 下一次加载会创建一个**新的** classloader，加载同名类。于是 JVM 里同时存在 `com.example.Foo` 的两个版本。

第二个后果会产生一类非常难读的异常：

```
java.lang.ClassCastException: com.example.Foo cannot be cast to com.example.Foo
```

同一个类名，不能互转 —— 因为它们来自不同的 classloader。看到这个报错的人第一反应通常是「这不可能」。

### 状态残留

- 插件注册的 listener 如果没在 `onDisable` 里反注册，`/reload` 之后仍然挂在事件总线上，指向一个「旧世界」的对象；
- 调度器里的 task 如果没取消，会继续跑；
- 打开过的文件句柄、数据库连接、缓存目录锁 —— 都可能还在。

结果是：**reload 之后行为取决于你的 `onDisable` 写得有多干净**，而大多数插件的 `onDisable` 只写了「保存配置」。

### 官方立场

Paper 官方文档明确不建议在生产环境使用 `/reload`，理由就是上面这些。mcsdev 服务的场景（开发验证）比生产更频繁 —— 一天 reload 五十次，类加载器泄漏会累积到可观测的程度。

## 冷启动有多慢

一个开发用的 Paper 服（少量插件、预生成或小世界）冷启动通常在几秒量级：

```
[12:00:00 INFO]: Done (3.412s)! For help, type "help"
```

对比 `/reload` 的「快但不可靠」，几秒钟换「确定加载了新代码」是明显划算的交易。

而且这个时间不是白花的：mcsdev 会**等端口真的可连**才继续。所以那几秒里你不是在等一个不确定的状态，而是在等一个被验证过的状态。

## 所以 mcsdev 把工程投入放在「让重启可靠」

如果重启是主路径，那么重启必须不折腾人：

| 问题 | mcsdev 的处理 |
| --- | --- |
| 重启把世界搞坏 | `dev` 自己拉起的实例走优雅停服（`stop` + 等保存）；Ctrl+C 也走同一条路 |
| 重启失败但看起来成功 | 重启后 TCP 探测端口，超时就报失败并指向 `logs/latest.log` |
| 每次构建都重启，太吵 | 没有文件变化就不重启（「产物无变化，跳过重启」） |
| 连续构建导致并发重启 | 串行化：一轮没跑完时只记一个「排队」标记 |
| 不知道重启有没有生效 | 日志里能看到「服务器已就绪（端口 25565 可连，等待 8s）」 |

这些都不是「让重启变快」，而是「让重启变得可信」。可信比快更重要：一个不可信的快路径会消耗你更多时间去验证它。

## 那什么时候可以用 reload

`mcsdev exec` 可以往运行中的服务器发任意命令（有 `dev` 会话时直接写服务器 stdin，否则走 RCON）：

```bash
mcsdev exec reload confirm
```

它有意义的场景是**代码没变**的时候：

- 改的是插件自己的配置文件（`config.yml`），而插件支持重载配置；
- 想快速看一下 `plugins` 列表、`tps`、玩家列表；
- 改的是数据文件（脚本、配方）。

它没有意义的场景是**jar 变了**：那必须重启。

所以 `exec` 的定位是「省掉一次整服重启的小操作」，不是「热重载方案」。文档里也按这个定位写它。

## 这条边界会一直存在吗

热重载不是「还没做」，而是「不值得做」。要让 reload 安全，需要：

- 类加载器层面的隔离（JVM 不支持卸载单个 classloader 的类）；
- 或者进程级隔离 + 状态外置（那就是另一个产品了）。

所以 mcsdev 不会提供「可靠热重载」。它提供的是：

1. 快而可靠的重启；
2. 不需要重启的操作走 `exec`（有 dev 会话时直接写服务器 stdin，否则走 RCON）。
