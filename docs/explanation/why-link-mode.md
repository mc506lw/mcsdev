# 为什么是 link 模式，而不是自己管服务器

mcsdev 默认不接管你的服务器：`link` 指向一个已经存在的服务器目录，它只往里放 jar 和触发重启。这个选择不是「MVP 简化」，而是对真实开发场景的判断。

## 真实的开发场景长什么样

一个 monorepo 里 8 个 gradle 插件子项目，共用一台外部 Leaf 开发服：

```
E:\Minecraft\开发\Pylon开发\
├── server.jar（Leaf）
├── server.properties
├── plugins\        ← 8 个插件的 jar 都在这
├── world\          ← 有测试用的存档、建筑、红石装置
└── logs\
```

这台服有几个特点：

- **它已经有状态**。世界、插件配置、玩家数据、op 名单。重建一台意味着这些都要重新准备。
- **它有自己的启停方式**。可能是双击一个 bat，可能是某个面板，可能是 systemd。写这套东西的人不一定是你。
- **它可能同时在给别人用**。团队里另一个人正在上面测别的东西。

在这种场景下，「工具帮我管服务器」不是帮助，是干扰。

## 如果 mcsdev 自己管服务器，要付什么代价

假设它接管启停，那么它必须知道：

- 用哪个 JDK、多少内存、哪些 JVM 参数（`-XX:+UseG1GC` 还是 Aikar's flags？）；
- 端口是多少（面板分配的？固定的？）；
- 世界目录叫什么（`world`？多世界插件改过？）；
- 启动前要不要跑某个脚本（备份？权限修复？）。

每一样都是猜。猜错的表现是「服务器起不来」或「起来了但不是你要的那台」，而这两种失败都很贵：你会先去怀疑插件，再怀疑 Java，最后才想到工具猜错了配置。

更根本的是：**同一台服不能有两个所有者**。如果 mcsdev 认为自己拥有启停权，而实际启停是面板做的，那么任何一次「mcsdev 重启失败」都会变成责任不清的事故。

## link 模式换来了什么

| 收益 | 具体表现 |
| --- | --- |
| 零迁移 | 不用搬世界、不用重配插件、不用改端口 |
| 和现有运维共存 | 你的 bat / systemd / 面板继续工作，mcsdev 只负责放文件 |
| 爆炸半径小 | mcsdev 的所有写操作都在 `<link>/plugins/` 下（外加重启） |
| 可撤销 | 删掉 `mcsdev.yml`，你的服务器毫发无损 |

最后一条值得强调：link 模式下 mcsdev 不是「基础设施」，它是一个可以随时扔掉的工具。这降低了试用成本，也降低了长期维护责任。

## link 模式付出了什么

代价是真实存在的，而且必须写在文档里：

### 1. 默认不重启（`restart.type: none`）

mcsdev 不知道你那台服怎么启停，所以默认只部署，并明确告诉你：

```
⚠ 重启策略是 none —— 每次部署后需要你手动重启服务器才会生效
```

要自动重启，你必须告诉它一条命令或一个 URL。这是把「不确定性」显式化：宁可让你写一行配置，也不要猜一个可能杀掉别人进程的命令。

### 2. 拿不到进程句柄，无法保证优雅停止

`restart.type: mcsdev` 时 mcsdev 自己拉起进程，所以能发 `stop` 等世界保存。外部服务器做不到这一点：

- `restart.type: command`：优雅与否取决于你的命令；
- `dev` 发现实例「由外部启动」时只能强杀，并且会警告：

  ```
  ⚠ 实例由外部启动，mcsdev 拿不到句柄，只能强杀（世界可能未保存）
  ```

  在 Windows 上强杀是 `taskkill /T /F` —— 世界确实可能没保存。所以外部服务器的推荐做法是用 `command` 调一个**自己会优雅停**的脚本。

### 3. 就绪探测连哪台机器，默认靠猜

「部署后确认服务器真的起来了」靠 TCP 探测。默认连 `127.0.0.1`，因为绝大多数开发服就在本机。

`link` 是 UNC 路径（`\\server\share\...`）时，默认取路径里的 `server` 当探测目标 —— 这是一个便宜但**不总对**的猜测：挂载路径里的 server 名不一定是 Minecraft 主机名。

猜错的表现是「部署成功，但等待就绪超时」。所以有一个显式的出口：

```yaml
host: 192.168.1.20
```

用 `host` 覆盖推导结果即可。这个字段只影响探测，不影响部署（部署永远是写本地路径）。

### 4. 无法验证「这个目录真的是 Minecraft 服务器」

mcsdev 只能做一个弱检查：目录里有没有 `server.properties`。没有就警告：

```
⚠ link 目录里没有 server.properties —— 这可能不是 Minecraft 服务器目录（E:\...）
```

它不会检查核心类型、版本、插件兼容性。判断目录对不对仍然是你的责任。

## 那 server 模式呢

`server` 模式（`mcsdev new` 建一台）解决的是另一个问题：**你还没有服务器**。

它的价值不是「比 link 模式更强」，而是「从零到能测」：

- 世界是干净的，测完可以 `reset` 重来；
- 端口自动分配，可以同时开多台做版本矩阵；
- 启停由 mcsdev 掌握，所以 `restart.type: mcsdev` 在 `dev` 会话里能优雅停服（它持有子进程句柄）。

  注意「持有句柄」这个前提：一次性的 `mcsdev deploy` 触发 `restart.type: mcsdev` 时，停止阶段是跨进程的（Windows 上 `taskkill /T /F`），拿不到 stdin，所以不保证优雅。

两种模式的命令集完全相同（`init / config / ps / deploy / dev / prune`），只有 `link` 那一段写法不同。这说明它们不是两套产品，而是同一个抽象的两个来源：**目标服务器从哪来**。

## 怎么选

```
你已经有一台跑着的开发服？
├── 是 → link 指向它的目录。配 restart（command 或 http），或接受手动重启
└── 否 → mcsdev setup + mcsdev new 建一台，link 指向实例名
```

还有一个常见组合：**先 link，后来才建实例**。这完全可以，改一行 `link` 即可，`plugins` 段不用动。
