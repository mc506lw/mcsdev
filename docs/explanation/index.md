# 理解

理解部分是**解释导向**的：它回答「为什么是这样」，不提供操作步骤。看完你应该能自己判断「这个场景该不该用 mcsdev」。

## 什么时候该看这个

- 你觉得某个默认值不合理（比如为什么 `clean` 默认开着）；
- 你想改设计，需要先知道当初为什么这么做；
- 你在向同事解释这套工具，需要一套站得住脚的理由；
- 你想知道它**不做什么**，避免用错场景。

## 一句话总结这些取舍

mcsdev 的每一个「奇怪」的默认值，都来自同一类失败：**静默的错误比显式的失败更贵**。

- 部署成功但服务器跑着旧代码 → 你会花半小时调一个不存在的 bug；
- 两个版本共存导致监听器执行两遍 → 你会怀疑自己的事件代码；
- 未实现的配置字段被静默接受 → 你会以为 `view-distance: 8` 生效了。

所以它选择：能探测就探测（端口）、能报错就报错（未实现字段、双载风险、未知 id）、宁可多删一个旧 jar 也不留下双载的可能。
